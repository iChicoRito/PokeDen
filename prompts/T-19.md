# Objective
## Remove Hard Authentication Barrier and Introduce Optional Account-Based Sync in Settings

---

## Role
You are a full-stack developer working on the Pokademia T-18 application. Approach this refactor with the mindset of a developer prioritizing user freedom, progressive onboarding, and seamless optional sync without breaking existing functionality.

## Description
The Pokademia T-18 application currently enforces a hard authentication barrier that requires users to sign in before they can access any functionality. The goal is to remove this barrier entirely so users can use the application freely from their first visit — creating task subjects, tasks, and other data that persists in the browser's local storage. Authentication becomes an optional, user-initiated action accessible from the Settings page, where users may sign in with their Google account to enable cross-device data synchronization. This separates the "use" experience from the "sync" experience, lowering the barrier to entry while preserving the value of an account for power users who need portability across devices.

## Primary Objective
Replace the mandatory sign-in gate with a fully open local-first experience, moving Google account authentication to the Settings page as an optional sync feature.

## Secondary Objectives
- Ensure all CRUD operations (task subjects, tasks, etc.) function entirely offline via local storage with no account required
- Implement Google OAuth sign-in in the Settings page that, when completed, syncs local data to the user's account
- Preserve existing Supabase integration (project `thdmmqdbtngrencwfqlw`, `tbl_profiles` with RLS) and its current sign-in at `/auth/sign-in`
- Maintain data integrity: local storage remains the source of truth until an account is linked and sync is triggered

## Success Criteria
- A new user can land on the dashboard and immediately create task subjects and tasks without any sign-in prompt
- All locally created data persists across page reloads in the browser's local storage
- The Settings page presents an optional "Sign in with Google" option
- Upon Google sign-in in Settings, the user's local data syncs to their Supabase-backed account
- The existing `/auth/sign-in` route no longer gates application access
- Existing authenticated users retain their data and experience no regressions

## Constraints
- Secrets (Google OAuth credentials, Supabase keys) must remain only in `.env.local` and never appear in source code or logs
- The existing Supabase project and `tbl_profiles` RLS policies must not be broken
- Local storage must handle data model changes gracefully (schema versioning or migration logic)
- Cross-origin and session state between local storage and Supabase must be handled carefully to avoid data loss or overwrite conflicts

## Out of Scope
- Building a new backend or replacing Supabase with another service
- Implementing real-time multi-device collaboration (only one-way sync from local to cloud on sign-in)
- Changing the data model of existing task subjects or tasks
- Supporting non-Google OAuth providers in this iteration

## Context & Dependencies
- The application is Pokademia T-18, a locally cloned project with main as the publish branch
- Supabase project ID: `thdmmqdbtngrencwfqlw`; table `tbl_profiles` has RLS enabled

- `.env.local` contains all secrets; Supabase CLI requires `sbp_` tokens only
- The local clone has `origin` (template upstream) and `chicofolio` (publish) remotes — only push main to `chicofolio`

## Stated Assumptions
- Users may freely use the application without any account — all data lives in browser local storage
- If a user accesses the application from a different device without signing in, their data will not be present on that device
- Signing in in Settings is the only path to cross-device sync; there is no forced or prompted sign-in elsewhere
- Google is the sole OAuth provider for this integration

## Detailed Breakdown

### Auth Gate Removal
Every component or route that currently checks for an authenticated session before rendering must be updated to render unconditionally. The auth check should be moved to an optional layer that enables sync features when a session exists, rather than blocking access when it does not. Existing session state (e.g., from a prior login) should still be detected and leveraged to provide sync functionality without re-prompting.

### Local Storage CRUD
Task subjects and tasks created while unauthenticated must be stored in the browser's local storage (or an equivalent client-side persistence mechanism). Each entity should include timestamps and a local UUID to support future merge with cloud data. The data model must account for a schema version field to handle future migrations gracefully.

### Settings Page Google Sign-In
The Settings page must present a clear, non-intrusive option to sign in with Google. Upon completion, the flow should:
1. Authenticate via Supabase Google OAuth
2. Retrieve any existing cloud data for the user
3. Compare with local data using timestamp-based conflict resolution
4. Push local data to cloud and pull any cloud-only data to local storage
5. Update the UI to reflect the synced state (e.g., show account email, sync status)

#### Nested Details
- If the user already has cloud data (from a previous device), the merge strategy must be clearly defined — the default should prefer the newer record per entity by `updated_at` timestamp
- If local storage is empty at sign-in, cloud data should be pulled down instead
- If the network fails mid-sync, the operation must be retryable without data loss
- Token refresh and session persistence must work across page reloads for signed-in users
