# Objective
## Parallel Multi-Agent Visible Browser Testing and Defect Remediation From Onboarding Through System Completion

---

## Role
You are a QA automation lead who orchestrates fleets of parallel agents and sub-agents. Approach this objective with the mindset, vocabulary, and priorities of that role: partitioning coverage into disjoint lanes, delegating exploration and implementation downward, and iterating test-and-fix cycles until the system is fully correct.

## Description
The system must undergo comprehensive end-to-end testing driven entirely through visible, real browser operation that the user can directly watch as it happens, rather than terminal-only or headless automation. A hierarchical fleet of parallel agents and nested sub-agents carries out both planning and implementation, with each agent owning disjoint files, components, or responsibilities to avoid conflicts without worktrees. The run begins at the onboarding screen with the system in a no-data state, proceeds through every module to the end of the system, exercises CRUD and all other exposed actions, and verifies each outcome. All errors, bugs, failed calls, broken integrations, edge cases, and regressions are audited, fixed, and retested until everything works correctly.

## Primary Objective
Drive the system through visible, watchable browser operation from the onboarding screen with no data through to system completion using parallel agents and sub-agents for planning, implementation, and testing, fixing every issue found and rerunning tests until everything works correctly.

## Secondary Objectives
- Use parallel agents with their own sub-agents for both planning and implementation phases.
- During planning, delegate system exploration to multiple parallel agents, each further delegating to its own sub-agents.
- During implementation, split independent work across parallel agents, each delegating its own work to its sub-agents.
- Avoid conflicts without worktrees by assigning separate files, components, or responsibilities to each agent.
- Visit every module and exercise representative functionality, including create, read, update, and delete operations.
- Audit every error, bug, non-functional behavior, and other issue encountered during the run.
- Verify the outcome of every action immediately after performing it.

## Success Criteria
- A complete browser-driven test run is executed in a visible browser the user can observe, starting from onboarding in a no-data state and reaching the end of the system.
- Every module has been visited and tested, with CRUD actions exercised and their results confirmed.
- Post-implementation testing has covered bugs, failed API calls, broken integrations, edge cases, and regressions.
- All issues found have been fixed and tests have been rerun until everything works correctly.
- A complete deduplicated audit records all errors, bugs, non-functional behaviors, and other issues, with every action outcome documented.

## Constraints
- Testing must be performed through real browser control in a visible, user-observable browser session, not through terminal-only, headless, or background automation.
- Work must be structured as parallel agents, each with its own sub-agents, at both planning and implementation.
- Do not use worktrees; prevent conflicts solely through disjoint assignment of files, components, or responsibilities.
- The run must begin at the onboarding screen with the system containing no data.
- Coverage must extend from onboarding through to the end of the system.
- The task may not be marked complete until tests pass with everything working correctly.

## Context & Dependencies
- The system under test is the current Pokademia web application in this workspace, accessed and driven through the browser.
- A delegation mechanism capable of spawning parallel agents and nested sub-agents is required before planning can begin.

agents

### Planning Phase
- [Sequential] Partition the system into disjoint exploration and test lanes, assigning separate files, components, or responsibilities to each agent.
- [Parallel] Delegate system exploration to multiple agents in parallel, each of which further delegates exploration to its own sub-agents.

### Test Setup & Entry Point
- [Sequential] Launch a visible browser session the user can watch and start control at the onboarding screen with the system in a no-data state.

### Implementation Phase
- [Parallel] Split the independent parts of the test implementation across parallel agents, each delegating its own work to its sub-agents.
- Progress through the system from onboarding to its end in the visible browser, visiting and testing every module within its owning lane.
- Perform create, read, update, and delete actions within each module and exercise all functionality each module exposes.
- Verify the result of every action immediately after performing it while keeping the browser behavior observable.

### Defect Audit
- Audit every error, bug, non-functional behavior, and other issue that occurs during testing.
- Document each finding, tagged by the agent or sub-agent and module that produced it.

### Post-Implementation Testing & Remediation
- [Parallel] Run thorough tests for bugs, failed API calls, broken integrations, edge cases, and regressions in the visible browser, delegating testing and debugging across parallel agents and their sub-agents.
- [Sequential] Fix all issues found.
- [Sequential] Rerun tests in the visible browser until everything works correctly, repeating the test-and-fix cycle as needed.

### Consolidation & Completion
- [Sequential] Collect all agent and sub-agent results, merge them into a single deduplicated audit, and confirm total coverage matches the full module set.
- [Sequential] Mark the task complete only after all tests pass with everything working correctly.
